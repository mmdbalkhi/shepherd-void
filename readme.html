1. Introduction

This is the only documentation this boot stack needs. It describes, end to end, how a single Void Linux root with a Guix-installed Shepherd 0.10.5 (and a Guile 3.0.9) comes up, and how to add a new service to it.1 Why not just use Guix System’s operating-system /services? Because owning dracut -> s6 -> Shepherd explicitly makes every failure mode legible and avoids Guix SD’s implicit service graph. This repo is that explicit graph.

A machine has one service manager, not three. Here it is #4, with s6 reduced to the smallest thing that makes that possible.

guix build shepherd resolves to the store path of Shepherd; the symlink keeps /usr/local/bin/shepherd stable across profile generations. guix build See the Guix manual for details on profile generation stability.

2. The three layers

+--------------------------------------------+
|         Layer 1: dracut initramfs          |
|  hardware discovery, storage, mount root   |
+--------------------------------------------+
                     |
                     |
                     v
+--------------------------------------------+
|           Layer 2: s6-linux-init           |
|    mount @gnu, @log, mkdir control dirs    |
+--------------------------------------------+
                     |
                     |
                     v
+--------------------------------------------+
|        Layer 3: GNU Shepherd 0.10.5        |
| root-rw, pseudo-filesystems, cgroups, udev |
+--------------------------------------------+

S6’s only job is Layer 2: bring the store and runtime writable, then hand control to Shepherd with (exec). Shepherd then runs the whole graph; s6 does not manage services. 

#!/bin/sh -e
# s6 stage 0 -> Shepherd handoff.  Regenerate with:
#   s6-linux-init-maker -b /etc/s6-linux-init/skel <more options>
DISK_UUID=abcd-...

# --- 1. mount what Shepherd/store need (idempotent) ---
mountpoint -q /gnu     || mount -t btrfs -o subvol=@/@gnu,noatime /dev/disk/by-uuid/$DISK_UUID /gnu \
                       || mount -t btrfs -o subvol=@gnu,noatime       /dev/disk/by-uuid/$DISK_UUID /gnu
mountpoint -q /var/log || mount -t btrfs -o subvol=@log,noatime       /dev/disk/by-uuid/$DISK_UUID /var/log
mountpoint -q /var/tmp || mount -t btrfs -o subvol=@tmp,noatime       /dev/disk/by-uuid/$DISK_UUID /var/tmp
mountpoint -q /var/cache || mount -t btrfs -o subvol=@cache,noatime   /dev/disk/by-uuid/$DISK_UUID /var/cache

# --- 2. exec Shepherd (PID 1) ---
SHEPHERD=/usr/local/bin/shepherd    # or /gnu/current-guix-profile/bin/shepherd
[ -x "$SHEPHERD" ] || exec /sbin/agetty --noclear -a root tty1 linux
mkdir -p /run/shepherd
"$SHEPHERD" -c /etc/shepherd/init.scm -s /run/shepherd/socket \
            -l /var/log/shepherd.log -I

The generator writes current/scripts/rc.init from skel/rc.init. Edit the skel copy and re-run s6-linux-init-maker. never patch current directly.

3. Shepherd’s graph

Shepherd does not have a “boot script”. It has a dependency graph and a target symbol that means “everything that must be up”; starting that symbol resolves and runs the whole graph in parallel.

The targets live in services.d/28-boot-stages.scm 2 Shepherd has no runlevel. A stage here is a service whose #:start is (const #t) i.e. a named barrier whose only purpose is its #:requirement, so the DAG is readable from one file. See info:(shepherd)Service Types and services.d/28-boot-stages.scm. 

;; 28-boot-stages.scm --- named barriers for the boot graph.

(define boot-critical
  '(root-rw pseudo-filesystems runtime-directories
    static-device-nodes kernel-modules cgroups udev udev-settle
    file-systems tmpfs swap sysctl dmesg guix-daemon))

(define boot-ready
  '(boot-critical hostname log-files syslog random-seed
    console-setup timezone hwclock))

(define interactive
  '(boot-ready agetty-tty1 agetty-tty2 agetty-tty3
    agetty-tty4 agetty-tty5 agetty-tty6))

(define fully-online
  '(interactive loopback dbus polkit elogind seatd acpid
    network-manager zram openssh chrony))

Boot DAG (what actually gates the gettys): 

                          root-rw
                       ───┬──────┬──────────────┐
         pseudo-filesystems cgroups    runtime-dirs
       (proc sys run dev ┌──cgroup2  (mkdir /run, /run/user
        dev-pts dev-shm  └──cgroup-v1 runtime-dirs)
        securityfs mqueue              │
        efivarfs)                      │
                       udev ─ udev-settle ─────────┤
                          │ static-device-nodes    │
                   file-systems ─ swap ────────────┤
                          │ hostname               │
                   log-files ─ syslog ─────────────┤
                 kernel-modules ─ random-seed ─────┤
                          │                        │
                      boot-ready ─ agetty-tty1..6 ─┤
                          │                        │
                interactive ─ loopback ─ dbus ─────┤
                          │            polkit  │   │
                 fully-online ─ network-manager ───┘

                   seatd · acpid · zram · ssh · chrony

The solid lines are #:requirement edges. Gettys depend on boot-ready, not on network/D-Bus/desktop, so a slow link or GUI never blanks the login prompt. udev is eudev from Void (Shepherd just supervises it); device nodes are pre-seeded by 05-static-devnodes.scm for udev’s very first run. Udev (ArchWiki) covers the rules format.

4. Add a service (template + worked example)

Every service is a (service '(provides) #:requirement '(...) #:start ...). That is the configuration: declare what it is, what it waits on, and what it does, and never a serial start ladder.

Template (copy to services.d/NN-name.scm): 

;; NN-name.scm --- one line.

;; Why it exists: <sentence>.  Why that dependency list: <edges>.
(define name
  (service '(name alias)
    #:documentation "Human sentence."
    #:requirement '(the-services-it-cannot-run-without)
    #:start  (make-forkexec-constructor '("name" "args" …)
                  #:log-file "/var/log/name.log")
    #:stop   (make-kill-destructor)
    #:respawn? #t))            ; one-shot? #t for transient steps

(register-services (list name))

Checklist:

  1. Add the file (zero-padded NN sorts before 28-boot-stages).
  2. Pick real provides (a list of symbols; not a string, not a list-in-a-list) and the minimal #:requirement.
  3. For daemons: argv list + #:log-file + make-kill-destructor + #:respawn? #t.
  4. For one-shots: use a pure Guile (lambda _ (zero? (system* ...))) or ~run-or-ignored~ + #:one-shot? #t + #:stop (const #t).
  5. Wire it into a stage: edit the #:requirement of interactive or fully-online’s stage in 28-boot-stages if it should be part of one.3 The stage #:requirement list is the “what must be up before X is considered up” contract. Add your symbol there to make it part of an ordered phase; leave it out and it only starts if something else pulls it in.
  6. Reload: herd load init.scm. Shepherd restarts only what changed; already-running services are untouched.

4.1. Template for One-Shots (mkdir, swapon, sysctl, etc.):

;;; NN-name.scm --- one-shot setup task.

(define name
  (service '(name)
    #:documentation "Human sentence."
    #:requirement '(the-services-it-cannot-run-without)
    #:start (lambda _
              ;; Pure Guile: no shell scripts, no make-system-constructor
              (zero? (system* "command" "arg1" "arg2")))
    #:stop (const #t)
    #:one-shot? #t))

(register-services (list name))

4.2. example: syncthing as a system service (4 Syncthing is a fine fully-online citizen: network-bound, not login-critical, restart-on-crash via #:respawn? #t. The example intentionally uses the system instance; for a desktop session move it to user-shepherd, set HOME and XDG_CONFIG_HOME, and require seatd. ):

;;; 31-syncthing-example.scm --- Syncthing daemon

;; Needs: network up (network-manager), persistent data on disk (file-systems),
;; and an unprivileged user + homedir.  Not required for login, so it lives in
;; ~fully-online~ and floats behind the gettys.
(define syncthing
  (service '(syncthing)
    #:documentation "Syncthing file synchronizer (system instance)."
    #:requirement '(network-manager file-systems)
    #:start (make-forkexec-constructor
             '("/usr/bin/syncthing" "-no-browser" "-gui-address=0.0.0.0:8384")
             #:log-file "/var/log/syncthing.log")
    #:stop (make-kill-destructor)
    #:respawn? #t))

(register-services (list syncthing))

To enable: cp the file into /etc/shepherd/services.d/, add syncthing to the fully-online stage requirements in 28-boot-stages.scm, then herd load init.scm. A new syncthing service appears in herd status with no Shepherd restart.5 syncthing/README · its systemd unit network-online.target + local-fs.target maps exactly to network-manager + file-systems here.

Syncthing ships a systemd unit that does the same network-online + filesystem dance; this is the manual port. For a per-user GUI session, put the same service under user-shepherd/services.d/ with GUIX_PROFILE set.

5. Runtime model (what you observe at boot)

  • /etc/shepherd/init.scm loads services.d/*.scm, then (start-in-the-background '(fully-online)).
  • Shepherd resolves requirements breadth-first and starts them concurrently where the graph allows.6 start-in-the-background (from services.d/init.scm) spawns a fiber that calls start-in-parallel: each node’s #:requirement starts first, and siblings with no edge between them start concurrently. Shepherd manual §“Dependency resolution”. You see interleaved Starting service X / Service X has been started. lines in /var/log/shepherd.log.
  • A service whose #:start throws is marked failed; dependents are skipped / retried, logged, and the boot continues on other branches. one bad daemon never hangs the whole boot.7 Failures are per-service. Shepherd logs Exception caught while starting X to /var/log/shepherd.log, marks the service failed, and continues other branches rather than aborting the boot. That is intentional: a one-shot random-seed failing must not stop udev.
  • boot-ready is the barrier behind which gettys wait; fully-online is everything else that is allowed to lag.
  • On shutdown, services run their #:stop thunks in reverse-dependency order (e.g., seedrng save, hwclock --systohc, cleaning /tmp).
$ herd status                   # on the running machine
root                            (running)   uptime 00:00:47
udev                            (running)   uptime 00:00:46
syslog                          (running)   uptime 00:00:45
boot-ready                      (stopped)   start it to unblock login
agetty-tty1                     (running)   uptime 00:00:44
fully-online                    (stopped)   start it to bring the rest
$ tail -f /var/log/shepherd.log  # the spinner feeds this
2026-... Starting service udev...
2026-... Service udev has been started.

Shepherd also exposes herd = the CLI. =herd help, herd doc <service>, and [[info:(shepherd)Invoking shepherd][info:(shepherd)]] cover every flag.

7. User Shepherd (Graphical Session)

While the system Shepherd manages the machine, the User Shepherd manages your graphical session (Sway, PipeWire, D-Bus, etc.). It runs as your regular user, supervising Wayland compositors and desktop daemons without needing systemd --user.

7.1. Session Flow

  1. init.scm sets XDG_RUNTIME_DIR and DBUS_SESSION_BUS_ADDRESS.
  2. 01-runtime-dirs ensures the runtime directory exists with strict 0700 permissions.
  3. 02-dbus, 03-pipewire, and 04-gpg-agent start in parallel (no GUI dependency).
  4. 05-sway starts the compositor (depends on dbus and runtime-dirs).
  5. 06-graphical-session barrier resolves once Sway is running.
  6. ALL GUI services (dunst, portals, swayidle, clipman, etc.) start in parallel.

7.2. Installation & Bring Up

# 1. Copy user Shepherd config and services to your home directory
mkdir -p ~/.config/shepherd/services.d
cp user-shepherd/init.scm ~/.config/shepherd/init.scm
cp user-shepherd/services.d/*.scm ~/.config/shepherd/services.d/

# 2. Ensure you are in the 'seatd' group (required for Sway to access input/DRM)
sudo usermod -aG _seatd $USER
# (Log out and log back in for group changes to take effect)

# 3. Start the user Shepherd daemon
shepherd -s /run/shepherd/$(id -u).socket \
    -c ~/.config/shepherd/init.scm -I

To start User Shepherd automatically on TTY login, add this to your ~/.bash_profile or ~/.profile: if [ -z "$WAYLAND_DISPLAY" ] && [ "$XDG_VTNR" -eq 1 ]; then exec shepherd -I; fi

7.3. Managing the Session

Because every component is a first-class Shepherd service, you can manage them individually without restarting the whole session: 

# Restart just the compositor (apps using DBus/PipeWire will survive!)
herd restart sway

# Check audio stack status
herd status pipewire wireplumber pipewire-pulse

# View compositor logs
tail -f ~/.local/state/shepherd/sway.log

8. Install & bring up (manual)

# 1. Shepherd config    ->    where rc.init expects it
cp services.d/*.scm           /etc/shepherd/services.d/
cp init.scm                  /etc/shepherd/init.scm

# 2. Shepherd binary visible to rc.init (one of:)
ln -s $(guix build shepherd)/bin/shepherd /usr/local/bin/shepherd       # Guix
# or:  ln -s $(which shepherd) /usr/local/bin/shepherd                  # Void

# 3. s6 stage 0 from the skel (regenerates current/scripts/rc.init)
s6-linux-init-maker -b /etc/s6-linux-init/skel \
  -u shepherd -g shepherd \
  -s /run/s6-svscan \
  -m /etc/s6-linux-init/monitor

# 4. Boot it (or reboot)
exec /etc/s6-linux-init/current/scripts/rc.init default
